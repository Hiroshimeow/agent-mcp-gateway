# HCU Multi-Account Device Control Plane Implementation Plan

> **For agentic workers:** implement phase-by-phase. Every phase has an independent review gate. Do not skip forward when a gate is red.

**Goal:** turn `agent-mcp-gateway` into the authenticated multi-account MCP control plane and `agent-mcp-device` into the explicit execution plane, with account-owned devices, strict IDs, invite-only signup, compact HCU device identity, usage/audit dashboard, and no hidden workspace/device fallback.

**Architecture:** ChatGPT connects only to `agent-mcp-gateway`. The gateway owns OAuth, accounts, invites, Superpowers/HCU skills, stable MCP tool contracts, device/project routing, usage aggregation, and dashboard. Each machine runs `agent-mcp-device`, which owns Ed25519 identity, pairing/login, WSS lifecycle, filesystem/edit/shell/process execution, and local runtime logging. YOLO is the default execution behavior **inside the authenticated account ownership boundary**.

**Tech stack:** Node.js/ESM, Node `sqlite`, Express/MCP SDK, TypeScript device runtime, WebSocket, Ed25519, scrypt password hashing, server-rendered HTML/CSS, Git/GitHub.

## Global constraints

- Public/wire identifiers use snake_case: `account_id`, `device_id`, `project_id`, `session_id`, `working_directory`, `timeout_ms`.
- Internal JS/TS may use camelCase, but conversion happens only at boundaries.
- `device_id` is immutable identity. New IDs are `<sanitized-hostname>-<random8>` and are authenticated by the device Ed25519 key.
- `device_name` is friendly and renameable; route by `device_id`, never by name alone.
- No important-ID fallback: missing `device_id` or `project_id` must fail closed when that identity is required.
- `list_devices` may help an agent resolve a friendly name/platform hint, but automatic routing is allowed only when exactly one compatible device exists.
- All normal users share the same product Superpowers/HCU skill catalog. No per-user skill ACL in this phase.
- YOLO remains the default runtime profile, scoped to devices owned by the authenticated account.
- Device ownership is enforced at dispatch on every remote tool call; this is an O(1) authorization check, not interactive reauthentication.
- Admin is local-CLI-only. The author uses a normal product account for normal MCP use.
- Signup uses email + password + single-use invite when `need_invite=true`; no email verification/password-reset workflow in this phase.
- Invite codes are 8-character uppercase unambiguous random strings, hashed at rest, single-use, revocable, generated by local admin CLI.
- Login UI is intentionally minimal/dark, but must not reveal whether an email exists.
- Login abuse protection is simple and non-global: rate/cooldown by account-key + source; do not let three bad guesses globally lock a victim account for an hour.
- Dashboard records metadata, not file contents, command text, or tool payload bodies by default.
- Token numbers exposed by the dashboard are explicitly estimates unless the source is exact bytes/counts.
- Do not publish npm in this phase. Target package identity is `@hcu/device` if the npm scope can later be owned; `@hcu-lab/device` is fallback.
- Deferred only: email invite-request approval flow, HA/failover implementation, GitHub Actions upstream watcher, npm publish, Linux-g8 production migration.
- Preserve legal attribution/licenses from Desktop Commander upstream.

## Phase 3 — Account, invite, login, OAuth subject, and ownership foundation

**Gateway additions:** account/invite/session persistence, admin CLI, login/signup routes, auth-provider refactor, pairing ownership.

- [x] Use one authoritative SQLite runtime DB (`gateway.sqlite`) for account/device/pairing/usage/auth metadata going forward.
- [x] Accounts: UUID `account_id`, normalized email, scrypt password hash+salt, role, revoked/deleted timestamps.
- [x] Invites: hash only, 8-char uppercase unambiguous code, created/used/revoked timestamps, single-use.
- [x] Config flag `need_invite` defaults to gated production behavior; when false signup does not require an invite.
- [x] Local CLI creates admin, lists/revokes/deletes accounts, creates/revokes invite codes. Admin has no public web login.
- [x] Product signup accepts email/password/invite; email verification is intentionally absent in this phase.
- [x] Product login uses the minimal dark progressive UI without account-enumeration signaling; signup/OUT remains available independently of whether the typed email exists.
- [x] Login failures use generic responses and simple source+account-key cooldown/rate limiting; no global three-strikes lockout DoS.
- [x] Browser account session is bound to `account_id`.
- [x] OAuth authorization requires an authenticated normal account session and tokens/refresh tokens carry `account_id` as the human subject.
- [x] Keep `offline_access`; access token 12h and refresh behavior remain durable unless intentionally revised/tested.
- [x] Device verify requires the same account session, then pairing approval writes `owner_account_id`.
- [x] Device table stores `owner_account_id`; existing account_label-only semantics are removed.
- [x] `list_devices` filters by authenticated `account_id`.
- [x] Every remote dispatch rechecks `caller.account_id === device.owner_account_id` in memory/authoritative state.
- [x] Static bearer cannot become a cross-tenant bypass; remote device calls require an explicit bound account or are denied.
- [x] Account revoke invalidates active account sessions/OAuth authorization and denies owned-device dispatch.

**Gate:** two-account tests prove Alice cannot list/call/revoke Bob’s device even when she knows Bob’s `device_id`; OAuth refresh preserves account identity; invite single-use/revoke tests pass; admin cannot log in through the public product UI.
